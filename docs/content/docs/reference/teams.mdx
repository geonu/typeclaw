Part of the [channel adapters](/docs/reference/channel-adapters) family.

Transport: **trouter WebSocket** for realtime inbound (no public URL required), with a **REST-only fallback** when realtime can't authenticate. Setup walkthrough: [Add a channel](/docs/guides/add-a-channel).

This is the **user-account** Microsoft Teams adapter (`teams`). It signs in as your own Teams user, so it hears every chat and team channel the account belongs to — no bot registration exists for Teams in agent-messenger, so this is the only variant.

<Callout type="warn" title="Use a dedicated account">
  This adapter signs in as a real Microsoft Teams user via device-code (AAD) login. It hears every chat and team-channel
  message the account can see, so run it only on a dedicated agent account. Access tokens live only 60–90 minutes; the
  device-code login captures an AAD refresh trio used to mint the realtime `id_token`, but the short-lived access token
  (skypetoken) itself is still refreshed by hand today — a long-running session needs `typeclaw channel reauth teams`
  (or a manual token swap) when it lapses.
</Callout>

## Auth

Device-code (AAD) login. `typeclaw channel add teams` prompts for the account type (work/school or personal), then walks you through a Microsoft device-code sign-in and stores the resulting token set in `secrets.json#channels.teams` as one or more account records. To rotate a stale token, replay the login with `typeclaw channel reauth teams`. (You can still populate the block by hand — e.g. from the [`agent-teams`](https://agent-messenger.dev/docs/cli/teams) CLI — but the interactive flow is the supported path.)

Unlike bot-token adapters, `secrets.json#channels.teams` is not a flat credential object — it wraps one or more account records:

```json
{
  "channels": {
    "teams": {
      "currentAccount": "<accountId>",
      "accounts": {
        "<accountId>": {
          "account_id": "<accountId>",
          "access_token": "…",
          "token_expires_at": "…",
          "account_type": "work",
          "region": "amer",
          "user_name": "…",
          "aad_refresh_token": "…",
          "aad_client_id": "…",
          "aad_tenant_id": "…",
          "created_at": "…",
          "updated_at": "…"
        }
      }
    }
  }
}
```

| Field                  | Notes                                                   |
| ---------------------- | ------------------------------------------------------- |
| `currentAccount`       | `string \| null` — active account id, or `null` if none |
| `accounts.<accountId>` | Map of account id → account record (fields below)       |

Each record under `accounts.<accountId>`:

| Field               | Notes                                                                     |
| ------------------- | ------------------------------------------------------------------------- |
| `account_id`        | Account identifier (matches the map key)                                  |
| `access_token`      | Current access token, expires in 60–90 minutes                            |
| `token_expires_at`  | _optional_ — access-token expiry timestamp                                |
| `account_type`      | `'work'` or `'personal'`                                                  |
| `region`            | _optional_ — `'amer'`, `'emea'`, or `'apac'`                              |
| `user_name`         | _optional_ — display name of the signed-in user                           |
| `aad_refresh_token` | _optional_ — AAD refresh token (reserved for a future unattended refresh) |
| `aad_client_id`     | _optional_ — AAD client id, needed alongside the refresh token to renew   |
| `aad_tenant_id`     | _optional_ — AAD tenant id, needed alongside the refresh token to renew   |
| `created_at`        | Record creation timestamp                                                 |
| `updated_at`        | Last-update timestamp                                                     |

The `aad_refresh_token` / `aad_client_id` / `aad_tenant_id` trio is captured by the device-code login and consumed at runtime to mint the realtime `id_token` in-container (see [Realtime](#realtime-inbound)); it is not yet used to auto-refresh the short-lived `access_token` (see [Token renewal](#token-renewal)). At minimum a record needs `access_token`, `account_type`, `created_at`, and `updated_at`; the rest are optional.

CLI: `typeclaw channel add teams` (interactive device-code login) and `typeclaw channel reauth teams` (replay the login to rotate a stale token). Teams is **not** part of `channel set` — its credentials are refreshed by replaying the login, not by pasting a token.

## Token renewal

Access tokens live 60–90 minutes. The adapter does **not** refresh the access token automatically today: on start it warns when the token is expired or expiring soon, and a long-running session stops delivering once the token lapses. To recover, replay the device-code login:

```sh
typeclaw channel reauth teams
```

(Or replace `access_token` (and `token_expires_at`) in `secrets.json#channels.teams` by hand — e.g. from the [`agent-teams`](https://agent-messenger.dev/docs/cli/teams) CLI — then restart the agent.)

The record also holds an AAD refresh trio (`aad_refresh_token`, `aad_client_id`, `aad_tenant_id`). The runtime adapter uses it to mint the realtime **id_token** in-container (see [Realtime](#realtime-inbound) below); the short-lived `access_token` (skypetoken) itself is still refreshed manually today.

## Realtime inbound

Realtime inbound rides Teams' internal **trouter WebSocket**. Authenticating that socket needs a second credential — an AAD Bearer "id_token" for the Teams/Skype spaces resource — separate from the `access_token` skypetoken. The upstream `agent-messenger` SDK obtains that id_token by scraping the Teams desktop app's cookie database (or a local browser profile), which is impossible in TypeClaw's headless container.

Instead, TypeClaw mints the id_token in-container from the stored `aad_refresh_token` via a standard AAD `refresh_token` grant — no desktop app or browser required. This needs the AAD refresh trio to be present on the account record (device-code logins capture it; legacy extracted-token accounts may not).

When the id_token can't be minted (no `aad_refresh_token`, an expired/revoked refresh token, or a trouter outage), the adapter **degrades to REST-only** rather than failing: outbound sends, history reads, and self-identity keep working, but the agent is no longer woken by inbound Teams messages until realtime recovers on the next start. A single warning is logged; there is no reconnect log-loop.

## Quirks

- **User-account, not a bot**: hears every chat and team-channel message the account can see, not just @mentions — engagement is governed by your `engagement.trigger` and match rules, not by a bot-mention model.
- **Chats and channels both**: unlike most user adapters, Teams covers both 1:1/group chats and full team channels; channel messages carry `teamId`/`channelId` and parsed @mentions.
- **Self-echo suppression**: the Teams user SDK has no self-identity boundary — `testAuth` returns the literal id `'ME'`, not a real MRI. Every successful send records a `(chat, normalized-text)` fingerprint, and a matching inbound arriving within a short window is dropped as the echo of our own send rather than routed as a new message.
- **Outbound is plain text**: Teams stores every message as HTML, so the adapter HTML-escapes what the agent writes. Markdown is not converted and Teams markup — `<at id="…">` mentions, `<a href>`, `<b>` — renders literally rather than as live markup, on chat sends, channel sends, and edits alike. This is deliberate: agent output routinely relays text written by channel users, and nothing in TypeClaw's outbound contract lets a caller opt into markup. Native mentions would need a structured mention field, not a format switch.
- **Realtime id_token is minted, not scraped**: the trouter socket needs an AAD Bearer id_token that the `agent-messenger` SDK would normally scrape from the Teams desktop app or a browser profile — neither of which exists in the container. TypeClaw mints it from the stored `aad_refresh_token` instead, and falls back to REST-only (send/read, no proactive inbound) when it can't. See [Realtime](#realtime-inbound).
- **Short-lived tokens, manual refresh today**: `access_token` expires in 60–90 minutes; the adapter warns on expiry but does not yet auto-refresh the skypetoken, so a long-running session needs the token rotated with `typeclaw channel reauth teams` (or replaced by hand in `secrets.json#channels.teams`). (The AAD refresh trio IS consumed for the realtime id_token above.)
- **Work vs personal accounts**: `account_type` distinguishes work/school tenants from personal Microsoft accounts; `region` records which AAD region issued the token.

## Config

```json
{
  "channels": {
    "teams": {
      "enabled": true,
      "engagement": {
        "trigger": ["mention", "reply", "dm"],
        "stickiness": { "perReply": { "window": 900000 } }
      },
      "history": {
        "prefetch": {
          "thread": { "head": 3, "tail": 10 },
          "channel": { "tail": 10 }
        }
      },
      "quotedReply": { "enabled": true, "queueDelayMs": 10000 }
    }
  }
}
```

All fields above are shared across adapters. No adapter-specific extensions exist for `teams`. Credentials live in [`secrets.json#channels.teams`](/docs/reference/secrets-json).
